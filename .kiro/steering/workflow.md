# 작업 규칙

## 브랜치
- 작업마다 최신 `main`에서 새 브랜치를 만들어요 (예: `feature/photo-upload`, `fix/community-sheet-buttons`). 머지된 브랜치는 다시 쓰지 않아요.
- 새 기능처럼 큰 작업을 시작할 때는 브랜치 이름을 사용자에게 먼저 확인해요. 머지 전 PR 에 대한 실기기 피드백 수정은 그 PR 브랜치에 이어서 커밋해요.
- `main`에 직접 커밋하지 않아요. PR은 `main`으로 보내요.
- PR은 **일반 머지(merge commit)**로 합쳐요. PR 설명의 되돌리기 명령이 커밋 번호를 쓰기 때문에, 커밋을 합치는 방식(squash)은 쓰지 않아요.
- 머지는 사용자가 실기기에서 확인했다고 한 뒤에만 해요.

## 커밋과 PR
- 커밋 메시지는 한국어로, `영역: 변경 내용` 형식이에요 (예: `마이 탭 9차: 톱니바퀴 · 설정에서 버전 빼기`).
- 항목마다 커밋을 나눠서 하나씩 되돌릴 수 있게 해요.
- PR 설명은 PR #5 형식을 따라요: 요약 · 바뀐 것 · 병합 전에 확인해 주세요(실기기 체크리스트) · 여기서 확인한 것 · 되돌리기 · 이번에 안 한 것.

## 확인
- 이 샌드박스는 Linux라서 Xcode 빌드와 실기기 테스트를 할 수 없어요. `swiftc -parse`로 문법만 확인하고, 바꾼 판단 로직은 앱 코드에서 떼어 Swift 로 돌려봐요. 빌드와 실기기 확인은 PR 체크리스트로 사용자에게 부탁해요.
- Firestore · Storage 보안 규칙을 바꾸면 `npm run test:rules` 테스트도 같이 고쳐요. 여기서는 npm 패키지를 받을 수 없어서(403) 규칙 테스트는 사용자가 맥에서 돌려요. `node` 는 `env -u NODE_OPTIONS node …` 로 실행해요.
- 새 Swift 파일은 만들지 않아요. Xcode 프로젝트 파일(`project.pbxproj`)이 파일을 하나씩 등록하는 방식이라, 기존 파일 안에 넣어요.
- 샌드박스의 `/tmp` · `/root` 는 명령 사이에 지워질 수 있어요. 검사용 임시 파일은 저장소 밖 워크스페이스(`/projects/sandbox/.verify`)에 두고 끝나면 지워요.
- 되돌리기 확인은 문법만 보지 말고, 되돌린 뒤 쓰는 곳은 남았는데 선언이 사라진 이름이 없는지도 봐요.
